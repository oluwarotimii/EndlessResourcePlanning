# Rules for working in this repo

Role-based retail front end on ERPNext. Read `docs/source/Product-Requirements.md` and `docs/source/Frontend-Plan.md` first.

- One task per pull request, under about 300 lines. Contract and tests first, then mock, then UI.
- **Design system (AURA):** never hard-code a colour, radius, size or motion value. Use tokens from `packages/tokens`
  (Tailwind classes such as `bg-primary`, `text-text-muted`, `bg-success-subtle text-success-ink`). `pnpm check:tokens` must pass.
  - Buttons use `btn-spring` and are at least 48px high (`min-h-touch`), 56px at the till (`min-h-till`).
  - Money, stock and counts use `tabular` (or the `<Money>` component).
  - Overlays and drawers use `glass-panel` / `scrim` (backdrop blur).
  - Text is never below 16px. Status is always icon + word + colour (`<StatusBadge>`).
- No ERPNext record names, user-facing text or brand strings outside the adapter, token files, `tenant.json` and `apps/web/src/i18n/en.ts`.
- The server is the authority; the UI only hides things. Hidden, never greyed out. Handle a refusal gracefully.
- Every screen declares its roles, offline behaviour and pattern (see `packages/permissions/src/data/screens.json`, generated by `pnpm fixtures`).
- Money, stock and approval actions carry a unique key so a retry never posts twice. Approvals and payouts are blocked offline.
- Money, permission and offline code is always reviewed by a human. No secrets in the cloud environment; mock server only.
- Roles and approval limits come from the spreadsheets in `docs/source/`, never from a second hand-kept copy.

## Documentation is part of the product (handover rule)
Any change to what the product does, to a setting, to a rule or to a decision must update the documents **in the same change**:
- `docs/PRODUCT-CHANGELOG.md`: add an entry (what changed, which documents were updated, what is open).
- `docs/DECISIONS.md`: edit the decision or open question.
- `docs/TENANT-CONFIG.md`: every `tenant.json` setting has a row (`pnpm check:docs` fails otherwise).
- `docs/SCREEN-STATUS.md`: run `pnpm docs:status` after building a screen; add a line in `docs/screen-status-notes.json` for a partly built one.
- `README.md` and `docs/PRINTING.md` when behaviour they describe changes.
- `docs/source/Product-Requirements.md` and `docs/source/Frontend-Plan.md`: append to their "Amendments" section when the requirement or plan itself changes. Never silently rewrite the original text.
- Say in the reply what was documented, and what could not be decided and was recorded as an open question.
Read `docs/HANDOVER.md` first if you are new to this repo.
