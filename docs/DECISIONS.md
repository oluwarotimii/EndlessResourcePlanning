# Decisions and open questions

**Not sure what a question means?** `docs/SCENARIOS.md` explains each open question as a short story with real numbers, the choices, my suggestion and a line for your answer. The stories are numbered; the table at its end says which question each story answers.

Current state only. When a decision changes, edit it here and add a line to `docs/PRODUCT-CHANGELOG.md`.

## Decisions made (confirm or change)
1. **Save first, then send.** Every sale is written to the device and queued before any network call. The receipt prints from local data. Offline selling and crash recovery are the same code path.
2. **Idempotency key per write, generated on the device.** An interrupted charge keeps its key so a retry cannot create a second sale. The server answers `duplicate: true` for a repeated key and changes nothing.
3. **Order is guaranteed per shift.** `shift.open`, sales and `shift.close` share the shift as record key and replay in order. If one fails for good, later items of that shift wait; other shifts continue.
4. **Identity rule.** Queued items replay only under the user who created them. If someone else signs in on the same till, the tray shows "waiting for <name> to sign in".
5. **Closing a shift signs the cashier out** (shared till). It first tries to sync; if offline, the closing waits in the queue for that cashier's next sign-in.
6. **Money is whole naira.** VAT handling is a company setting (`tax.mode`: inclusive, exclusive, none), rounded half up, one shared function. The server is the authority and rejects a mismatch.
7. **A sale has a list of payments.** They must add up to the total. `credit` needs a customer with credit terms and room under the limit. Only the `cash` portion counts toward expected cash in the drawer.
8. **Credit limit is enforced twice.** On the device from the last customer data it saw (may be stale offline) and by the server when the sale syncs. If the server rejects it after the goods left, the item shows as failed in the sync tray for a manager.
9. **Payment is only recorded for now.** Transfer and card are recorded at the till. Live confirmation arrives with Paystack (Sprint 9), so the "confirmation within 10 seconds" target cannot be tested yet.
10. **Failed money items are never discarded** by the cashier. The resolution workflow is a Sprint 3 question.
11. **Own contract, not raw ERPNext records.** The ERPNext adapter (Sprint 5) maps to our contract.
12. **Approvals are an online, deliberate decision.** The inbox shows the requester, the exception, the amount, the limit and the customer; approval needs a hold-to-confirm, rejection needs a reason. Every decision carries an idempotency key, the creator can never decide their own request, and the server checks the approve letter on the relevant area (`Stores (POS)` for discounts, `Returns` for voids, `Credit sales` for over-limit credit). Approvals are blocked offline. Limits are read from configuration, not from code. A cashier raises a discount or void request from the till (S05); nothing changes there until it is approved. An approved discount applies to the gross subtotal before VAT, exactly once, and any cart edit clears it. An approved void clears the cart.
13. **Closing balance is a blind count, then a approval by someone else.** The cashier counts the cash by note first and only then sees the expected cash and the difference. Closing a shift IS the closing balance (Q01): it queues the close (works offline) and signs the cashier out. The server recomputes the expected cash (opening balance plus cash payments), requires the notes to add up to the count, and requires a reason when the count does not match. Closing raises a closing balance approval (kind `cash_up`) in the manager's inbox and in Q02; the cashier can never approve their own count.
14. **Who approves a closing balance (DEFAULT CHOSEN, please confirm).** The journey says "the cash controller or manager" and screen Q02 lists the Branch manager, but the matrix gave only Cash controller and MD the Approve step. I chose to let **both the Branch manager and the Cash controller** approve, by adding `A` for Branch manager on Closing balance through `packages/permissions/src/data/matrix-amendments.json` (merged by `pnpm fixtures`; the spreadsheet itself is untouched). If the owner decides otherwise, edit that file or correct the spreadsheet and run `pnpm fixtures`.
15. **Manager home and the variance report are read-only, server-computed figures.** The screens only display them and keep the last good copy on the device, marked "Saved figures", so they open offline.
16. **Who approves what is a setting, decided later by the owner.** Each kind of approval has ordered steps naming the roles allowed to decide each step (`packages/permissions/src/data/approval-routing.json`, explained in `docs/APPROVAL-ROUTING.md`). Rules: the requester never decides; one person never decides two steps; a rejection ends the chain; amount limits still apply per approver; an unlisted kind falls back to the matrix Approve letter. This supersedes decision 14: the closing balance approver is now just a line in that file (default: Branch manager or Cash controller).
17. **Refunds will use the same routing** (planned kind `refund`), so the owner can require more than the manager, for example the manager then a second role. Not built until T01.
18. **A refund is what the customer actually paid for the returned lines** (a share of the sale total by the lines' share of the subtotal), so an approved discount and VAT added on top are respected. The server recomputes it and ignores the client's figure.
19. **Every return needs an approved refund, used once.** The approval is tied to the sale and the exact lines; it follows the routing setting (default: two steps, Branch manager or MD, then Cash controller or MD). The per-item limit is compared with the largest returned line.
20. **Refunds and the drawer.** A cash refund lowers the expected closing balance; card, transfer and other refunds do not. If part of the sale was on credit, that share reduces what the customer owes first and the rest is paid back by the chosen method.
21. **Returns and stock requests need a connection.** A refund needs another person's approval (approvals are blocked offline), and stock requests are online-only in the screen inventory.
22. **Stock moves by transfer, with two people at each hand-over.** A branch asks (H02); the warehouse packs and sends (H03); the branch counts what arrived (H04). The requester cannot dispatch their own request and the dispatcher cannot receive their own transfer.
23. **A shortage is flagged, never hidden.** Receiving less than was sent records a shortage on the transfer; an item nobody counted counts as none received; counting more than was sent is refused.
24. **Dispatch and receiving work offline,** saved on the device and queued with an idempotency key, like sales. The saved list of requests and transfers is what an offline device works from.
25. **Warehouse stock and shelf stock are separate numbers.** Dispatch lowers warehouse stock; receiving raises shelf stock by what was counted. (In the mock the warehouse starts with three times the shelf quantity.)
26. **A shortage is ruled on, not charged automatically.** Receiving short opens a ruling (approval kind `shortage`) for someone independent of the branch (default Auditor or MD, a placeholder). The ruler chooses who bears the loss (branch, warehouse, transport). Only a ruling against the branch is charged to the branch's figures. Rejecting (with a reason) charges nothing.
27. **The loss is valued at cost, and cost is hidden from the branch.** The value at cost is shown only to the people who rule on it. The ruling follows the stock write-off limit (₦100,000, above it the MD). Deducting from an individual's pay is a separate decision outside the system (legal limits in Nigeria).
28. **Everything is built with ERPNext in mind.** Each build adds or updates a row in `docs/ERPNEXT-MAPPING.md`, marked Owner (from the owner's documents), Seen (confirmed from ERPNext documentation) or Proposal (unverified, to confirm on staging). Open ERPNext questions are collected at the end of that file.
29. **The approvals inbox follows the approval setting.** Anyone named in a routing, or holding the matrix Approve letter, sees the inbox (A01); anyone who can approve a closing balance sees Q02. Before this, the Auditor and the Cash controller could not reach the inbox.
30. **A stock count is blind, then recounted by a different person.** The sheet has no system quantities. Items that differ come back for a recount by someone other than the first counter (setting `stock.recountByDifferentPerson`); the recount is the final figure. Until the count is final the counter never sees the expected quantity.
31. **A difference changes stock only after approval.** The Stock controller asks (K02); the approval follows the routing setting (`write_off`, default two steps, a placeholder); stock is set to the counted quantity only when the last step approves. Rejecting adjusts nothing and closes the count.
32. **The value at cost is hidden from the counter** and shown to the people who approve. A leak found by a test (the cost was returned in the response to the person who asked) was fixed by one shared function used everywhere an approval is returned.
33. **Counting is open to anyone who may create counts** (not only the Stock controller), so a different person can do the recount. Approving a write-off stays with the routing.
34. **A rider's delivery is proved in 3 taps and works offline.** Deliver, (cash on delivery: the full amount is already chosen), Confirm. A cash-on-delivery order must collect the full amount or be marked failed; a prepaid order takes no cash; a failed delivery needs a reason and returns to the coordinator to be assigned again. The proof is saved on the phone and queued (`delivery.proof`).
35. **Delivery cash is confirmed by a manager.** The rider hands in the cash and records it; a manager or the cash controller confirms (approval kind `cash_remittance`, a routing setting). Until then it shows as outstanding; after the time limit (`delivery.codRemitHours`) it shows as overdue. Rejecting frees it to be handed in again.
36. **Variant items must be scanned.** Setting `till.scanRequiredForVariants` (on): a tile cannot add an item that has variants; the cashier scans the barcode on the item. The count screen and the write-off approval flag "possible mix-up" when one variant is short and its sibling is over, so a swap is not read as theft. A correction flow for a mix-up is planned, not built (Scenario 13).
37. **The offline cache ignores `Vary`.** A bug found in the real-browser test: the browser sends an `Origin` header when loading a lazy screen and the server marks files `Vary: Origin`, so a file cached at install never matched, and a screen not yet opened online failed offline. The service worker now matches with `ignoreVary` (cache `erp-shell-v3`).
38. **There is a written spec of the Frappe custom app** (`docs/FRAPPE-APP-SPEC.md`). Every API path the mock exposes must be listed there (checked by `pnpm check:docs`).
39. **Owner's answers to the scenarios (2 Nov).** Follow the suggestions in `docs/SCENARIOS.md` for stories 1 to 12 and 14 as placeholders until the system is configured. Every list of reasons is a setting that can grow (add as many as needed). The Cash controller is a real role. Who approves is always a permission, never a person or a fixed role: "anybody with the permission may approve". The MD and Auditor may rule on losses; leave that as is. The Auditor does not approve the closing balance by default (Scenario 3, B). Ambiguity to confirm: the owner wrote "let us stick to the A"; read as Scenario 2, A (the cashier records the opening balance, the manager sees it in the morning summary).
40. **Return days are a rule by category or product (built: server check and settings; no settings screen yet).** The number of days a return is accepted must be settable per product category and per product, with a company default. Setting `returns.rules`: most specific wins (product, then category, then default), with separate days for faulty items. The server refuses a refund request outside the window and says how many days are allowed. A manager override and a screen to edit the rules are not built. Scenario 16.
41. **A faulty return goes to RMA or back on the shelf, by a named inspector (not built).** Faulty returns go to a check area first. The person who inspects (Stock controller or Auditor, assigned by permission or by name) decides: RMA (sent back to the supplier) or restock. Scenario 16.
42. **Credit partners bill a third party (not built).** Some credit sales are billed to a credit partner (for example Credit Direct) rather than to the customer. The sale carries a "bill to" party. Some items may be billed to any party, others only to certain ones. Scenario 17.
43. **A Credit control officer approves credit sales, depending on the account (not built).** Approval routing for credit becomes per account (customer or credit partner): each account names its approver and limit. Anybody holding the permission may approve. Scenario 17.
44. **Permissions are assigned, not hard-coded.** Approvers, inspectors and rulers are assigned to roles or to named people in the configuration console (planned Sprint 10). Until then the routing file holds the placeholders (`docs/APPROVAL-ROUTING.md`).
45. **CR01: the over-limit credit request is raised from the till.** When a credit sale would go over the customer's available credit, the cashier can ask a manager from the same needs-manager dialog used for discounts and voids (S05). The request carries the customer and the amount over the limit; once approved, the approval is tied to that customer and amount and can be used for one sale only (a second attempt, or a different customer, is refused). The sale carries the approval's id so the server can check it. Per-account approvers and credit partners billed to a third party are not built (decisions 42, 43).
46. **H01: goods receipt is built the standard ERPNext way, against a purchase order (no requirements text existed for this screen).** The spreadsheets and the plan say only that H01 is a "Build custom" scan flow for the Warehouse officer, mapped to ERPNext's Purchase Receipt; nothing else was written about it anywhere in the source documents. Rather than invent a bespoke flow, it follows ERPNext's own Purchase Order → Purchase Receipt pattern: a purchase order (supplier, lines, quantity ordered) is received against, scanning what arrives; receiving less than ordered is normal (the rest may come in a later delivery, so the order stays "partly received"); receiving more than the order plus a configured allowance (`stock.overReceiptAllowancePercent`, placeholder 0) is refused, matching ERPNext's "Over Receipt Allowance". Raising and approving a purchase order is the separate, later screen R01 (supplier onboarding is R02); until R01 exists, purchase orders arrive at H01 already open, seeded in the mock. **Deliberately not built:** an accepted/rejected (damaged-goods) split on the receipt line (ERPNext supports this when quality inspection matters, but there is no inspection data here); what happens to goods rejected at the door (return to the supplier, akin to the unbuilt T02); and any approval step on receiving itself (unlike the branch-transfer shortage ruling, there is no second internal party to a supplier delivery, so screens.json lists only the Warehouse officer for H01, not two roles as it does for H04).
47. **A branch can also ask a sister branch for stock, not only the warehouse (H02-H04 generalised; not in any source document).** Nothing in the spreadsheets or the plan describes moving stock between two branches — the only stock-transfer journey written down is "the warehouse packs and sends"; the mock had modelled only one branch (see "Branch scoping" among the open questions, below). The owner asked for this directly: a branch should be able to request stock from a sister branch and sell it once received, the same way it already asks the warehouse. Built by generalising, not duplicating, the existing screens:
    - **H02** gets a "Request from" choice (the warehouse, or a named sister branch); choosing a sister branch shows what that branch currently holds, per item, before asking (the owner's choice, over asking blind). This runs inside H02 itself, not H05, because Branch manager (who raises H02) has no screen-level access to H05 in the owner's spreadsheet, even though the server permission letter (`Warehouse` "V") already covers them.
    - **H03** is unchanged in shape: whoever packs and sends still scans and confirms. Who *may* pack a sister branch's request is the sister branch's own **Warehouse officer** (a second demo user, `u-warehouse2`, "Bayo Fashola" at "Victoria Island Branch", PIN 3334) — not its Branch manager, because H03's role list in the owner's spreadsheet is Warehouse officer only, and that list is not something this build may hand-edit (`docs/FRAPPE-APP-SPEC.md` section 6 / `CLAUDE.md`: roles come from the spreadsheet). A request is only dispatchable by someone whose own branch matches where it was addressed (a sister branch's stock draws from that branch's own pool, never the central warehouse); this closed a real gap, so a warehouse-bound request was also tightened to require someone actually tied to the warehouse (`user.warehouse` set) — previously any Warehouse-letter role could technically call the dispatch endpoint. H03's own list of waiting requests is filtered the same way, so nobody is shown a request they cannot act on.
    - **H04** (receiving) is unchanged; it now also shows which sister branch sent a transfer, when one did.
    - **Not built:** a dual-control rule between two branches (the sister branch's single officer both decides to send and does the sending, same as the warehouse today — there is no "requester cannot dispatch" equivalent beyond the existing "you cannot dispatch a request you raised" check, since the two branches are different people by construction); any approval before stock leaves a sister branch (the owner chose none, matching today's warehouse flow); and the deeper "branch scoping" gap already on record (a manager still sees every branch's sales and closing-balance figures, not only their own).

## Open questions for the business
- **VAT:** which `tax.mode`, what rate, and who confirms it (accountant)? Are some items VAT-exempt (not supported yet; the mode applies to the whole sale)?
- **Credit:** real credit limits per customer and who sets them; whether the cashier or the manager may sell on credit; whether credit needs a deposit. The over-limit request from the till (CR01, decision 45) is built; per-account approvers and credit partners (decisions 42, 43) are not.
- **Offline prices:** a sale made offline uses the price the till last saw. If the real price changed meanwhile, accept or send to a manager? The mock accepts the till's price.
- **Offline sign-in:** signing in needs a connection (the PIN is checked by the server). A cashier already signed in keeps working offline, including after a reload. Do tills need to sign in offline (for example after a power cut)? That needs a locally stored PIN check and a security decision.
- Closing balance variance **reason codes** (requirements, open question 6): the cashier now picks a reason when the count does not match, but the list in `cashUp.varianceReasons` is a **placeholder** (counting error, change given wrongly, cash taken for an expense, unknown). Return reason codes are still undecided.
- **A rejected closing balance** has no recount flow yet. It is recorded as rejected with the manager's reason, and the shift stays closed. Who recounts, and what happens to the drawer, needs a business rule.
- **Closing balance process roles (owner to decide, then set in `approval-routing.json`).** Candidate design from the owner's description: the Branch manager is responsible for the **opening** cash (issuing or confirming the float), the **closing** count is approved by the **Auditor** (independent), and whoever **deposits** at the bank counts it again (Q03, Sprint 7). Open points: (a) does the manager only record the opening balance, or must they confirm it before the cashier may sell (not built; it would block selling offline unless confirmed on the device); (b) the Auditor is read-only and independent in the matrix, so approving is a control choice for the owner; (c) one step or two (for example manager then Auditor).
- **Branch scoping.** A manager sees every closing balance and the whole day's figures; the real system must scope them to the manager's branch. The mock now has two branches for stock purposes (decision 47: Pilot Branch and Victoria Island Branch), but sales, shifts, closing balance and reporting are still built as if there were only one; a real multi-branch rollout needs that scoping done properly, and a real list of branches from the owner.
- **Returns:** the real list of return reasons (the one in `returns.reasons` is a placeholder); the return window (how many days after a sale a return is allowed); whether returned goods go back on the shelf or to quarantine (the mock does not restock; quarantine is Sprint 7); whether returns may happen offline; a printed credit note; and who the refund route should name (the default two steps are a placeholder).
- **Goods receipt (H01):** the real over-receipt allowance (`stock.overReceiptAllowancePercent`, placeholder 0); who raises and approves a purchase order (R01, not built; they are seeded in the mock for now); and what happens to goods rejected at the door (return to the supplier, or an accepted/rejected split with quality inspection) (decision 46).
- **Transfers:** what happens to the part of a request that was not sent (today it is not re-requested); where missing items go (a loss or quarantine record, Sprint 7); whether a request can be cancelled; how long a transfer may stay unreceived before someone must act (the alert time is a setting, `stock.inTransitAlertHours`); and the low-stock level (fixed at 5 in code for now).
- **Branch-to-branch requests (decision 47):** the real list of branches and which hold their own stock (one demo sister branch, "Victoria Island Branch", stands in for now); whether a sister branch needs any approval before sending its stock, or any dual control beyond "you cannot dispatch your own request" (today: none, matching the warehouse flow); and whether a shortage on a branch-to-branch transfer should open the same independent ruling it does for a warehouse transfer (today: yes, unchanged, since H04 receiving is the same code path either way).
- **Shortage rulings:** who rules (the default Auditor or MD is a placeholder), how long they have (`stock.shortageRulingHours`, 48 hours is a placeholder), what happens if nobody rules in time (today it only shows as overdue; it is not charged automatically), and whether the transport (carrier or rider) can really be charged. Whether staff are charged personally is a separate legal and HR decision.
- **Stock counts:** the cut-off while stock is moving (the count compares with the quantity at the time it is submitted; sales and transfers during a count can create false differences, so counting when it is quiet is advised); how often counts happen and which items (a full count or a cycle by category); whether a second difference after the recount triggers an investigation; and who approves write-offs (the default two steps are placeholders).
- **Delivery:** the real failed-delivery reasons (mine are placeholders); how long a rider may hold cash (`delivery.codRemitHours`, 24 is a placeholder); who confirms delivery cash (default Branch manager or Cash controller); and whether a customer who short-pays may keep the goods with the difference owed (today the rider must collect the full amount). See Scenario 14.
- **Variants:** should a mix-up correction need approval and from whom; who covers the price difference if the customer has left; whether every variant has its own barcode on the item. See Scenario 13.
- Offline limits (50 unsynced sales, 12 hours) are placeholders.
- Which payment methods appear at the till (requirements, open question 5): five are available; the real list goes in `till.paymentMethods`.
- The pilot branch, real approval limits, the A5 printer and whether silent printing works on the till computer (requirements, open questions 1, 2, 8).
- **Approval expiry and visibility:** how long a pending request stays valid, and whether approvers should see requests outside their branch. The mock keeps requests until decided and shows the role everything it may decide.

## Problems found in the source documents (not yet corrected there)
1. **Closing balance approval.** (Handled by default; confirm.) The matrix gave the Branch manager `VCE` on Closing balance (no Approve) while the journeys and screen Q02 have the manager signing off. Decision 14 adds the Approve step for Branch manager through a documented amendment file. The spreadsheet should still be corrected by the owner.
2. **Rider screens.** The inventory lists "Rider" for L02 and L03; the matrix role is "Rider / courier". The importer maps it.
3. **Screen counts.** The Screens sheet has 97 rows but the Summary says 93. The build uses the 93 actual screens.

## Known gaps
- The approvals inbox, the S05 discount/void request and the CR01 over-limit credit request are all built from the till. The returns screen raises its own refund approval (T01) but no other screen outside the till raises a request yet.
- Camera barcode scanning is not built; keyboard-wedge scanners work.
- Silent printing is documented but not verified on real hardware.
- The e2e test is a script, not yet in CI (CI has no browser installed).
- Mock-only: PIN sign-in, capabilities, every endpoint. Nothing talks to ERPNext yet.
